# 9. `next-themes` and `lucide-react` are the only two web dependencies beyond the named stack

Date: 2026-09-11 · Status: accepted

## Context

`AGENTS.md` names the interface stack and forbids substituting it: Next.js 15 App Router,
Tailwind, shadcn/ui, AI SDK `useChat`. It also requires an ADR for any new runtime dependency.
Those two rules meet at a question the stack line does not answer: shadcn/ui is not a package
that gets installed, it is components copied into `web/components/ui/`, and several of those
components import things. Installing shadcn/ui and installing nothing else are not the same
act, and pretending otherwise would put undeclared packages in `package.json` under cover of a
rule that was meant to prevent exactly that.

Two are needed before the first screen, and both come from decisions already made elsewhere in
this repository rather than from taste.

**A theme switch.** `web/app/theme.css` carries a full dark palette, because
`docs/artefacts/interface-design-pack.html` shipped one and Zee's week-8 task requires WCAG AA
in *both* themes. A theme that only follows `prefers-color-scheme` cannot be tested in both on
one machine, and a person who chooses light on a dark laptop is entitled to get light. The
switch has to write a class onto `<html>` **before first paint**, or every load of a dark
screen flashes white — which is a blocking script, `localStorage` read, and hydration guard
that we would be writing ourselves.

**Icons.** `reference/craft-floor.md` and ordinary sense both rule out emoji standing in for an
icon system. Four navigation destinations, a lock, an eye, a close, and the three problem
states need about a dozen glyphs at one consistent stroke weight.

## Decision

`web/package.json` declares exactly two runtime dependencies beyond the named stack:

| Package | Why it is here | Licence |
|---|---|---|
| `next-themes` | Sets the theme class before first paint; three states, not two | MIT |
| `lucide-react` | shadcn/ui's own icon set, tree-shaken per icon | ISC |

Both are shadcn/ui's documented defaults — `components.json` records `"iconLibrary": "lucide"`,
and the shadcn dark-mode guide for Next.js *is* `next-themes`. Choosing differently would be
the substitution the stack rule forbids, not compliance with it.

`clsx`, `tailwind-merge` and `class-variance-authority` are not on this list because they are
not a choice: `cn()` in `web/lib/utils.ts` is generated by shadcn's own `init`, and every
component it emits imports it. They are part of the named stack, arriving under its name.

Nothing else gets added to `web/package.json` without superseding this record. In particular
there is no date library, no icon second-guessing, and no component kit beyond shadcn.

## Alternatives considered

| Option | Why not |
|---|---|
| Write the theme switch by hand | The hard part is not the toggle, it is the inline script that must run before paint, the `localStorage` read, the `suppressHydrationWarning` on `<html>`, and the system-preference listener. That is the same fifty lines `next-themes` ships, only ours would be the version nobody else has debugged — and getting it wrong shows up as a white flash on a dark screen, not as a test failure. |
| `prefers-color-scheme` only, no switch | Removes the dependency and the ability to check both themes on one machine. Zee's week-8 task says "in both light and dark"; a reviewer would have to change an OS setting and reload between every check. It also silently overrides a person who wants light on a dark machine. |
| Inline SVG icons, hand-drawn | Viable, and it is what `web/components/wordmark.tsx` does for the one mark that is genuinely ours. Across a dozen UI glyphs it stops being drawing and starts being maintaining an icon set at a consistent stroke weight, which is a job nobody in this lane has time for and which `lucide-react` does correctly by default. |
| An icon font | One request, but it ships hundreds of glyphs to deliver twelve, cannot be tree-shaken, and renders as a missing-glyph box before it loads. |

## Consequences

`package.json` is now a closed list that a reviewer can read in ten seconds, and the "no new
runtime dependency" rule has a written boundary on the web side instead of an argument every
time somebody adds a screen. Both packages are MIT/ISC, which is what Siew's provenance review
needs, and both are already what a shadcn `add` would have pulled in silently.

The cost is two packages that must be kept current, and a theme implementation this team did
not write. If `next-themes` is abandoned, the replacement is the fifty lines above rather than
a redesign — the only thing it owns is a class on `<html>`, and `web/app/globals.css` reads
that class through one `@custom-variant`, which is the entire coupling.

The larger cost is the one this ADR exists to make visible: **"shadcn/ui" in `AGENTS.md` is not
a package, so the stack line under-specifies the web lane.** Anybody adding a shadcn component
that imports something new is adding a dependency, and they now have to come here rather than
deciding alone. That is friction on purpose.

## Revisit when

A shadcn component the interface genuinely needs imports a third package — Radix primitives are
the likely one, arriving with a dialog or a select. `web/components/source-chip.tsx` currently
uses the native `<dialog>` element specifically to avoid that, and if a surface needs behaviour
the native element cannot give, the addition belongs in a record that supersedes this one.
