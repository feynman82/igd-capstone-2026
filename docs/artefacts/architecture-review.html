RAG at the core, two axes of expansion

The architecture your team decided on, written down. Retrieval is the platform. Capability modules extend it sideways, domain packs extend it downwards, and both plug in through a declared contract rather than by editing core code.

The one consequence of decision 7 worth saying out loud

Tracker, Alert and Reminder read typed rows: dates, amounts, policy numbers, owners. They cannot read chunks. So even with retrieval as the core and the modules as add-ons, the core still has to extract typed fields at ingest and write them to a facts table, or there is nothing for a module to attach to. This is not a return to the four-primitive framing; it is a statement about what the core RAG platform must include for the expansion story to be buildable rather than aspirational. It costs the core one pipeline stage and one table.

02

The expansion model

This is the answer to "how far can this go", and it is the strongest slide in the deck. One core, two independent axes. Adding a capability module makes every existing domain pack more useful. Adding a domain pack makes every installed module apply to a new part of household life. Neither requires touching the other, and neither requires touching the core.

Why two axes and not one list

A flat list of features has no story about growth. Two axes give you a multiplication table: 13 named extensions produce far more than 13 capabilities, because every module applies to every pack that registers it. Insurance plus Reminder is renewal warnings. Insurance plus Alert is a coverage gap crossing a threshold. Tax plus Tracker is deductions year to date. You build four things and demonstrate a combinatorial surface, which is exactly the argument a platform proposal has to make.

It also gives you a clean answer to the question a supervisor will ask, which is where this stops. It stops at Actions. Everything up to and including Alert observes and advises. The moment a module can transact, the governance case changes completely, and Section 10 says so explicitly rather than leaving it as an unexamined edge.

03

Architecture

Nothing has been removed from the ambition. What has changed is that the boundary is drawn, and everything that crosses it is labelled with when it ships.

How to phrase the privacy claim now

Replace "zero-telemetry, offline privacy" with this: "Documents, extracted facts, embeddings and all model inference remain on the user's hardware. Capture channels are transports only: media is fetched, filed locally, and deleted at source. Google Drive access, when enabled, is read-only and scoped by OAuth to a single folder." It is defensible line by line, it survives someone reading the architecture diagram next to it, and it is what IMDA's agentic framework asks a system to publish. An unqualified offline claim next to a Drive integration is the kind of thing that costs you the room.

04

The VRAM budget, with headroom

You asked for buffer so the demo works. Swapping to a 4B model does more than buy headroom: the whole stack now fits on one 8 GB laptop GPU, which means the demo path and the product claim finally describe the same machine. A local-first household assistant that needs an 18 GB workstation is a research prototype; one that runs on a laptop is a product.

Three consequences worth putting in the report. No layer splitting at all. The eGPU is no longer needed for inference, which removes the per-token traffic over the narrowest link in the machine and one whole class of demo-night failure. Context capped at 16K. The model offers 256K, but nothing in a household question needs it once retrieval has narrowed the evidence to six reranked passages, and the KV cache grows linearly. The 27B stays in the report, not the demo. Benchmark it, publish the quality comparison, explain why the smaller model was chosen. A measured trade-off reads as engineering judgement; an unmeasured claim of comfort reads as optimism.

The swap buys a capability, not just headroom

Qwen-SEA-LION-v4-4B-VL is a vision-language model, so it can read a document image directly rather than only the text Docling extracted from it. Do not replace Docling with it — Docling is faster, cheaper and better at tables from digital PDFs. Use it for the case Docling cannot handle: give the quarantine queue a second pass through the VLM. A faint scan or a phone photo that failed layout parsing gets one more attempt from a model that looks at the pixels. That turns quarantine from a dead end into a two-stage pipeline, and it is a genuinely interesting result to report either way — how many quarantined documents a vision model recovers is a number nobody else in the cohort will have.

05

Document pipeline

Unchanged from revision 1, and it is the stage that makes the expansion model buildable. Every document produces searchable chunks for the RAG core and typed rows for whichever capability modules are installed. The two commit together, so a reminder can never disagree with a search result.

Two details worth defending in the report. Contextualising chunks before embedding is a measured technique: Anthropic reported a 35% reduction in retrieval failures from contextual embeddings alone, 49% combined with contextual lexical search, and 67% with reranking added.[13] Cite theirs as the motivating result and measure your own. Extraction through a JSON schema rather than prompt-and-parse: Ollama constrains generation to the schema at decode time, which is what makes a 4B model reliable enough to write into a date column.[14] That constraint is doing more work now than it was: a smaller generator is a weaker free-form writer but an equally obedient schema filler, so the extraction quality survives the model swap in a way prose fluency would not.

One addition the swap makes possible. Quarantine is now a second pass rather than a dead end. The generator is a vision-language model, so a document that fails layout parsing or falls below the OCR confidence floor is re-attempted against the page image. Docling is not replaced — it is faster, cheaper and better on digital PDFs, and it handles the common case. The vision pass exists for the faint scan and the phone photograph taken at an angle, and the proportion of quarantined documents it recovers is a reportable finding.

06

The domain pack manifest

A pack that is only a system prompt is a persona with better branding. This is the contract that makes it a plugin. Every field is either consumed by the core at a defined point or enforced as a guardrail; there are no decorative keys.

Worked example

# packs/insurance_agent/pack.yaml
id: insurance_agent
version: 0.2.0
display_name: Insurance and Coverage
owns_document_types: [policy_schedule, renewal_notice, claim_letter, benefit_illustration, rider_endorsement]

extraction:
  model: packs.insurance_agent.schemas:PolicyDocument
  writes: [facts, obligations]

grounding:
  corpus: grounding/mas_fair_dealing_and_product_summaries/
  top_k: 6

registers:
  reminder: { obligations: [{ key: policy_expiry, from_field: expiry_date, lead_days: [60, 30, 7] }] }
  alert:    { thresholds: [{ metric: uncovered_months, ceiling: 0, warn_at: 1.0 }] }
  # tracker not registered — this pack has nothing meaningful to aggregate

persona:
  system: >
    You review the user's own policy documents and explain what they say.
    You compare coverage against what the documents state, never against products you recall.

guardrails:
  must_cite: true
  abstain_below: 0.45
  never_acts: true
  disclaimer: >
    Informational analysis of your own documents. Not financial advice under the
    Financial Advisers Act. Confirm coverage with your insurer or a licensed adviser.

Why Tax and Insurance are the two to build

Tax is the only pack with objectively checkable ground truth. IRAS relief rules are public, rule-based and versioned by Year of Assessment, and payslips and CPF statements are highly structured, so the golden set has answers that are unambiguously right or wrong. That is what makes your accuracy number mean something. Insurance is the one every household in the room recognises, its documents are the messiest realistic input you will find, and it registers a different combination of modules from Tax. Building those two proves the contract holds across genuinely different domains, which is exactly what a single pack cannot demonstrate. Note that Caregiving, Legal and several others declare no grounding corpus: they answer only from the user's own documents, which is itself a designed guardrail rather than a gap.

07

The capability module contract

The second axis needs its own contract, and it is deliberately smaller than the pack contract. A module declares what it reads, when it runs, and what it renders. It never touches retrieval, and it never writes facts.

# modules/reminder/module.yaml
id: reminder
version: 1.0.0
reads: [obligations]           # typed rows only. Modules cannot read chunks.
writes: [schedule]              # its own namespace, never facts
runs: { on: schedule, cron: "0 7 * * *" }
surfaces: [today, notification, chat_thread]
config_schema: modules.reminder.schemas:ReminderConfig
# packs supply the config; the module supplies the behaviour
Built · week 4

Reminder

Reads the obligations table nightly, compares due dates against each pack's declared lead times, and surfaces what is inside the window. The single highest-value module: it is what makes the assistant speak first.

Built · week 5

Alert

Runs on fact write rather than on a schedule. Compares a computed metric against a pack-declared ceiling and fires once per crossing, with a debounce so it cannot repeat daily.

Specified

Tracker

Aggregates typed rows over a period with parameterised SQL. Deferred because it is the least surprising of the three to a reviewer, not because it is hard.

One rule governs all three: the number is computed by PostgreSQL, never written by the model. Parameters are extracted into a typed structure and bound into hand-written, reviewed SQL. The model's only job is to phrase the sentence around a figure it did not produce. This is why a household assistant built this way can be trusted with a renewal date in a way a purely generative one cannot, and it is worth a sentence in the presentation.

08

Query flow and grounding

The RAG core owns the answer path. A module only intercepts when the question is explicitly about a schedule or a total; everything else is retrieval, and retrieval can decline.

The grounding gate is the single feature most worth demonstrating. Below the pack's reranker floor the system states that it has no document that answers, rather than composing something plausible from weak context. In the trace log this is one line and one decision; in the room it is the difference between a tool a family would trust with a will and a tool they would not.

09

The golden set

Agreed as the evaluation harness. Three datasets, built from your own documents, run at three fixed points so the report shows movement rather than a single number.

Set A · 60 items

Answerable

Known answers in your corpus. Split across the RAG core and both built modules, and across both built packs, so the table breaks down by component.

Set B · 25 items

Hard negatives

Questions the corpus cannot answer. Scored purely on whether the system abstains. This is the set that proves the grounding gate.

Set C · 15 items

Adversarial

Prompt injection inside an ingested PDF, a request to act rather than advise, and an invitation to claim a relief the documents do not support.

Ragas with a judge served locally through Ollama's OpenAI-compatible endpoint, so no evaluation question leaves the machine.[11] Runs land in weeks 3, 5 and 8. Note the two module metrics: adding capability modules to the architecture means adding rows to this table, and a reviewer who sees a module measured takes the expansion story more seriously than one who sees it only drawn.

The number to lead with

Not accuracy. Abstention rate on Set B. Every commercial assistant in that room will confidently invent an answer to a question its evidence does not cover. A local system that says "I do not have a document that says" is making an argument about trust that no benchmark score can make on its behalf, and it is the argument this module is actually about.

Governance

Four layers, and the ISO layer now cites both standards with the right work attributed to each. That distinction is a slide on its own, and it is the kind of precision that separates a team that read the standard from one that read a summary.

ISO/IEC 22989 stages and ISO/IEC 5338 processes, side by side

22989 supplies the life-cycle stage vocabulary. 5338 supplies the processes, and explicitly does not prescribe a life cycle; the stage names commonly attributed to it are 22989's, appearing in 5338 only as an illustrative figure. Presenting them as two complementary standards is both accurate and more interesting than presenting either alone.

Above the ISO layer, IMDA's 2024 framework for generative AI sets nine dimensions, and a local-first architecture answers the data governance dimension structurally rather than procedurally. IMDA's framework for agentic AI, launched 22 January 2026, is the one that speaks directly to a system with tools, memory and modules; its four dimensions are risk assessment and bounding, human accountability, technical controls, and end-user responsibility.

Your risk-bounding statement is now unusually clean, because the expansion model draws the line for you: the Actions module is specified and deliberately not built. Everything shipped observes, retrieves and advises. Nothing transacts. That is a documented autonomy boundary rather than an absence, and every pack enforces it with never_acts: true in its manifest, which means the boundary is machine-checked and not merely asserted in prose.

Working with Antigravity

Three things that save a week

Write both contracts before the first extension. An agent given the pack manifest and the module manifest produces consistent code across sessions; given prose it produces three different designs.
Golden set before features. A failing eval is a specification an agent can work against. "Make retrieval better" is not.
Boring libraries. Postgres, FastAPI, Next.js and LangGraph are heavily represented in training data, which matters more than usual when an agent writes most of the code.
