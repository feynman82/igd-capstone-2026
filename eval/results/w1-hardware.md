## How to read this

**Decode tok/s** is `eval_count / eval_duration` as Ollama reports it, so it excludes model
load and prompt processing. Median of 3 runs after 1 warm-up run,
`num_predict` 256, temperature 0.

**Peak VRAM** is whole-device `nvidia-smi memory.used`, sampled every
100 ms for the life of the request, worst of the measured runs.
The WDDM driver on Windows reports per-process VRAM as `N/A`, so the model's own share cannot
be isolated directly — the **Model VRAM** column subtracts the idle baseline instead, which
is an estimate and is labelled as one.

**Context** is `num_ctx`. Ollama allocates the KV cache for the whole window at load time, so
peak VRAM rises with `num_ctx` regardless of prompt length. Decode rate does not behave the
same way, which is why the filled row exists: it is the same window with the prompt actually
occupying it, and it is the honest figure for the configured operating point of
16K.

**Placement** is the `PROCESSOR` column of `ollama ps`. Anything other than 100% GPU means
layers spilled to CPU and the decode figure on that row is a number about this machine's
memory pressure rather than about the model.

## The operating point

At the configured 16K window the generator holds
5.6 GB and decodes at 91 tok/s with the window
84 per cent full. That is the figure to
plan against, not the short-prompt row above it.

Raising the window to 32K costs 2.3 GB more VRAM for no
decode gain — the
short-prompt rows differ by less than the run-to-run spread — so the window is a memory
decision, not a speed one.

With the generator and the embedder (`embeddinggemma:300m`) both resident, the device holds
7.3 GB of 10.0 GB. The reranker (`hf.co/gpustack/bge-reranker-v2-m3-GGUF:latest`) is not in that
figure: `core/graph/baseline.py` still returns passages unchanged, so there is no call to
make and a number for it would be invented rather than measured. Whoever wires it adds a row.

## What this is for

Yew Mun sizes the evaluation run against the decode rate, and the grounding gate's latency
budget is set from it. The 4B is the generator in `core/runtime/settings.py`; there is no
second generator measured here.
